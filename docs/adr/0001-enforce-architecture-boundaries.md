# レイヤー・モジュール境界を決定論的に検査する

## 状態

採用済み。

- 判断日: 2026-11-03
- 合意: 本セッションで提示した境界チェック方針に対する、同日のユーザーの「採用」。
- 現時点ではアプリ本体がないため、本ADRは方針の採用を記録する。チェックの実装・CIへの組み込みは未実施。

## 背景

バックエンドは、クリーンアーキテクチャーに準拠したレイヤーを持つモジュラーモノリスとする。
フォルダー配置やレビュー時の注意だけでは、禁止された依存の追加を防げない。
機械で判定できる境界ルールは決定論的に検査し、人のレビューは責務の適切さや仕様の妥当性に集中させる。

## 決定

### コンパイル時の制約

- レイヤー・モジュールの境界に応じてプロジェクトを分け、必要な参照だけを与える。
- 内部実装は可能な範囲で`internal`にする。
- `internal`の境界はアセンブリであり、複数アセンブリからなる業務モジュール全体を保護するものではない。
  レイヤー間の連携に必要な公開型を、他モジュールから利用させない制約は参照検査とアーキテクチャーテストで補う。

### 参照設定の検査

- プロジェクト参照とパッケージ参照を、明示した許可リストと照合する。
- 禁止された参照を追加してコンパイル時の制約を迂回する変更も、検査失敗とする。
- 推移的な依存まで禁止するルールでは、プロジェクトファイルだけでなく復元後の依存グラフも検査する。

### アーキテクチャーテスト

コンパイル済みアセンブリの型の依存関係を解析し、少なくとも次のルールを検査する。

| 対象 | 禁止する依存・利用 |
|---|---|
| Domain | Infrastructure、Presentation、EF CoreやASP.NET Coreなどの技術層 |
| Application | Infrastructureの具体実装 |
| Presentation | DbContextなどのInfrastructureの具体実装 |
| モジュール間 | 他モジュールの内部実装。連携は公開されたモジュール間契約を介する |

- 起動・DI構成に必要な具体実装への参照は、明示した構成部分に限定して許可する。
  例外のためにPresentation全体を検査対象から外さない。
- 検査するアセンブリを明示し、対象の型が存在することも検証する。
  対象が0件であるために成功する検査を認めない。
- 各ルールとテストの対応を追跡できるようにする。
- 導入時には、意図的に禁止依存を持つ独立した検証用コードなどで、違反を検出できることも確認する。
  検証用の禁止依存を本体へ混入させない。
- 通常のテスト実行に組み込み、CIでも違反を失敗として扱う。

### 適用範囲と未決事項

- この決定は境界の強制方法を対象とする。具体的なプロジェクト数、モジュール一覧、
  公開契約の配置、許可リストの内容、テストライブラリは実装前に具体化する。
- NetArchTestなどのライブラリは候補であり、本ADRでは特定のライブラリを採用しない。
- 動的なリフレクションや、生SQLによる他モジュールのテーブル参照まで、
  型の依存関係の検査だけで完全に防げるとは扱わない。
- DBの境界は、データ所有方針と合わせてスキーマ、DB権限、統合テストなどで別途設計する。
  スキーマの分離だけをアクセス禁止の保証とはしない。

## 重要な代替案と不採用理由

- 文書と人のレビューだけに頼る: 判定可能な違反を継続的・一貫して検出できない。
- プロジェクト参照だけに頼る: 禁止参照の追加や、モジュール間の公開型の不適切な利用を防ぎきれない。
- 型の依存関係のテストだけに頼る: 未使用の参照設定や動的なアクセスなど、検出できない違反がある。

## 影響・トレードオフ

- 依存の制約を文書、コンパイラー、参照検査、テストで整合させて保守する必要がある。
- 責務の分割や業務モジュールの妥当性は、人のレビューで判断する。
  自動チェックの成功を設計全体の妥当性の証明とはしない。
- 境界ルールを変更する場合は、合意済みの設計判断と検査を一緒に更新する。
  チェックを通すためだけに例外を広げない。
- CIへの検査追加と、GitHubのruleset・ブランチ保護による必須化は別である。
  リポジトリ設定は明示的な許可なしに変更しない。
